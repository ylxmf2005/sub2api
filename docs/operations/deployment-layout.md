# Deployment Layout

This document describes the standardized server-side workspace structure for the Sub2API private fork deployment.

## Workspace Structure

The production deployment should be contained within a single directory (e.g., `/opt/sub2api/` or `~/sub2api/`). This "local directory" layout ensures that all data, configuration, and orchestration files are kept together, making backups and migrations straightforward.

```text
sub2api/
├── .env                        # Production environment variables (secrets)
├── docker-compose.local.yml    # Upstream base compose file
├── docker-compose.private.yml  # Private fork override file
├── data/                       # Application runtime data (logs, uploads, etc.)
│   └── logs/                   # Application log files
├── postgres_data/              # PostgreSQL database files
└── redis_data/                 # Redis persistence files
```

### Components

| File/Directory | Description |
|---|---|
| `.env` | **Critical.** Contains all production secrets and configuration. Must be secured (e.g., `chmod 600`). See `deploy/private/.env.production.example` for a template. |
| `docker-compose.local.yml` | The canonical base configuration provided by upstream. Uses local directory mounts for persistence. |
| `docker-compose.private.yml` | The private override that specifies the `sub2api-private` image and any host-specific integrations (like the datamanagementd socket). |
| `data/` | Mapped to `/app/data` in the container. Stores the runtime state, including the `config.yaml` generated by `AUTO_SETUP`. |
| `postgres_data/` | Mapped to `/var/lib/postgresql/data`. Contains the live PostgreSQL database. |
| `redis_data/` | Mapped to `/data`. Contains the Redis AOF/RDB persistence files. |

## Deployment Commands

Always use both compose files together to ensure the private overrides are applied:

```bash
# Start the stack
docker compose -f docker-compose.local.yml -f docker-compose.private.yml up -d

# View application logs
docker compose -f docker-compose.local.yml -f docker-compose.private.yml logs -f sub2api

# Stop the stack
docker compose -f docker-compose.local.yml -f docker-compose.private.yml down
```

## Migration & Continuity

The use of local directories instead of Docker named volumes allows for "filesystem-level" migration:

1. Stop the services.
2. Archive the entire workspace directory.
3. Transfer and extract on the new server.
4. Update `.env` (if necessary) and start the services.

**Warning:** When migrating, ensuring that `.env` secrets (`JWT_SECRET`, `TOTP_ENCRYPTION_KEY`) are identical to the old server is mandatory to preserve user sessions and 2FA validity.
